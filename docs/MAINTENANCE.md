# Cyberhack — заметки по поддержке

## Что это за проект

Cyberhack — это самостоятельный npm-пакет: React-компонент `<Cyberhack />` с игрой
"Взлом протокола" (Breach Protocol, как в Cyberpunk 2077). Игровая логика (генерация
доски, правила буфера, таймер, подсчёт награды) написана на Rust поверх Yew и
скомпилирована в WebAssembly; `Cyberhack.tsx` — тонкая React-обёртка, которая лениво
подгружает wasm-модуль, монтирует его в `<div>` и получает результат обратно через
`window.postMessage`.

Это **не часть VPN-ядра и не критичный для отказоустойчивости сервис** — судя по
пропсам (`redirectUrl`, `baseValue`, начисление `total_coins`/`₴`) это мини-игра для
геймификации/вознаграждений где-то на маркетинговой поверхности продукта (скорее
всего используется из netrunner-landing или похожего фронтенда как способ выдать
пользователю бонус/промо-код за прохождение). Публикуется как отдельный npm-пакет
`cyberhack`, ставится через `npm/yarn/pnpm add cyberhack` в любое React/Next.js
приложение — независимо от остальных репозиториев netrunner.

Важно: в коде явно предусмотрен **server-authoritative режим** (пропсы `matrix` /
`targets` / `sessionId`) — расчёт награды на основе `total_coins`, приходящего от
клиента, не является безопасным (клиент может просто прислать поддельный
`postMessage`). Если через эту игру реально начисляются деньги/бонусы, потребитель
пакета обязан использовать server-authoritative режим и пересчитывать награду на
бэкенде по `result.path`, а не доверять `result.total_coins`. Подробности — в
README.MD, раздел "Server-authoritative mode".

## Структура репозитория

- `src/lib.rs` — вся игровая логика на Rust/Yew (генерация доски, правила ходов,
  таймер, локализация ru/en, `#[wasm_bindgen]`-точка входа `initCyberHack`,
  юнит-тесты).
- `Cyberhack.tsx` — React-компонент верхнего уровня (публичный API пакета), лениво
  грузит `cyberhack/wasm`, рисует канвас-фон (hex-дождь) ещё до загрузки wasm, слушает
  `window.postMessage` для получения результата партии.
- `index.ts` — точка реэкспорта (`Cyberhack`, `CyberhackProps`, `CyberhackResult`,
  `CyberhackTheme`) — то, что реально импортируется как `from "cyberhack"`.
- `index.html` + `run_app()` в `src/lib.rs` (feature `standalone-debug`) — отдельная
  debug-страница для `trunk serve`, не имеет отношения к продовой сборке пакета.
- `index.d.ts` (в корне) — **устаревший файл, мёртвый код**, см. раздел "Грабли" ниже.
- `styles.css` / `main.css` — исходник и собранный (Tailwind v4) CSS для debug-страницы
  (`trunk serve`), не то же самое, что `pkg/cyberhack.css`, которая идёт в npm-пакет.
- `Cargo.toml` / `Cargo.lock` — Rust-часть (`wasm-bindgen`, `yew`, `rand`,
  `gloo-timers`, `serde`).
- `package.json` — dev-манифест репозитория (скрипты сборки, `pnpm dlx`,
  devDependencies для Tailwind/`concurrently`). Не публикуется в npm.
- `package.publish.json` — шаблон манифеста, который реально попадёт в npm-пакет
  (копируется в `pkg/package.json` скриптом `sync:config` с подстановкой актуальной
  версии из `package.json`).
- `pnpm-lock.yaml` / `pnpm-workspace.yaml` — репозиторий использует **pnpm**, а не
  npm, несмотря на то что часть скриптов исторически названа `npm run ...` в README.
  `pnpm-workspace.yaml` на момент написания этого файла — untracked (не добавлен в
  git), содержит одну настройку (`allowBuilds` для `@parcel/watcher`); не трогать его
  git-статус при работе с остальными файлами.
- `pkg/` — **полностью генерируемая директория** (результат `wasm-pack build` +
  `prep:pkg` + `sync:config`), ничего из неё не закоммичено (у неё есть собственный
  `pkg/.gitignore` с `*`). Это и есть содержимое итогового npm-пакета: `cyberhack.js`,
  `cyberhack_bg.wasm`, `cyberhack.d.ts` (сгенерирован `wasm-bindgen`, описывает только
  низкоуровневый `initCyberHack(element_id, config_json)` и wasm-init-обвязку),
  `cyberhack.css`, плюс скопированные `Cyberhack.tsx`/`index.ts`.
- `target/` — стандартный Cargo build-каталог, в git не попадает.
- `images/preview.png` — картинка для README.

## Как собрать / запустить / протестировать локально

Требуются: Rust + Cargo, `wasm-pack`, Node.js, `pnpm`. Для debug-страницы
дополнительно нужен `trunk` (`cargo install trunk`) — в песочнице/CI по умолчанию
его может не быть, `pnpm run dev` без него не заработает.

```bash
# установка зависимостей (именно pnpm, см. выше)
pnpm install

# полная продовая сборка: wasm (--no-default-features) + tailwind css +
# копирование TS-обвязки в pkg/ + генерация pkg/package.json
pnpm run build

# только wasm
pnpm run build:wasm

# только css
pnpm run build:css

# debug-страница на Rust/Yew через Trunk (порт 8080), с watch на Tailwind
pnpm run dev

# бамп patch-версии в package.json и полная сборка
pnpm run release

# Rust unit-тесты (генерация доски, подсчёт награды, фолбэк локализации)
cargo test
```

На момент проверки (2026-07-19) `cargo test` — 4/4 зелёных
(`test_calculate_coins`, `test_board_generation_size`,
`test_board_contains_valid_tokens`, `test_dict_fallback`).

Локальной проверки конечного npm-пакета (`npm pack` / установка в тестовое
приложение) в репозитории не настроено — если нужно проверить, что `pkg/`
действительно рабочий пакет, придётся собирать и подключать вручную (`pnpm link`
или `file:` зависимость в другом проекте на `./pkg`).

## Переменные окружения / конфиг

Отдельных `.env`/секретов у этого репозитория нет — это чистый клиентский пакет без
серверной части. Вся конфигурация приходит не через env, а через пропсы React-
компонента `<Cyberhack />` (см. README, раздел "Component Props") либо через JSON,
который `Cyberhack.tsx` формирует и передаёт в `initCyberHack` на стороне wasm
(`GameConfig` в `src/lib.rs`): `redirect_url`, `base_value`, `time_limit`, `locale`,
`theme`, `matrix`, `targets`, `session_id`.

Единственный "конфиг" уровня сборки — Cargo feature `standalone-debug`
(`Cargo.toml`, включена по умолчанию): она компилирует debug-автозапуск игры
(`run_app()`) прямо в `document.body`. Продовая сборка (`build:wasm` в
`package.json`) обязана передавать `--no-default-features`, иначе получится второй,
независимый экземпляр игры, смонтированный в body любого приложения, которое
подключит пакет (это реальный баг, который уже чинили — см. раздел "Грабли").

## Известные грабли / TODO / технический долг

1. **`index.d.ts` в корне репозитория — мёртвый и устаревший файл.** Описывает
   старый низкоуровневый API `initCyberHack(elementId, configJson)` /
   `mountGame(elementId, config)` со snake_case-конфигом (`CyberHackConfig`,
   `redirect_url`, `base_value`, ...) версии 1.0.0 (последний раз менялся в коммите
   `c530912 "1.0.0"`). Реальный публичный API пакета — React-компонент `Cyberhack` с
   camelCase-пропсами из `Cyberhack.tsx`/`index.ts`, и он давно ушёл вперёд (появился
   server-authoritative режим, `sessionId`, `result.path` и т.д., которых в
   `index.d.ts` нет вообще). Файл нигде не референсится — ни в `package.json`, ни в
   `package.publish.json` (там `types` указывает на `./index.ts`), ни из кода. Он
   просто лежит в репозитории и вводит в заблуждение при первом знакомстве с
   проектом. **Стоит удалить его или явно пометить как deprecated** — не делал этого
   в рамках задачи по актуализации доков, чтобы не трогать лишние файлы, но это
   первый кандидат на уборку.
2. **Нет CI/линтера/форматтера в репозитории** — ни `.github/workflows`, ни
   `clippy`/`rustfmt` конфигурации, ни eslint/prettier для TS-части. Единственная
   проверка — `cargo test` руками.
3. **Тесты покрывают только чистую Rust-логику** (генерация доски, награда,
   локализация). Нет никаких тестов на `Cyberhack.tsx` (React-обёртка, обработчик
   `postMessage`, ленивая загрузка wasm) и нет интеграционных/e2e тестов на полный
   игровой цикл клика по клеткам. Ошибка парсинга `postMessage` в `Cyberhack.tsx`
   молча проглатывается (`catch (e) {}`), что упрощает жизнь (не мешают чужие
   `message`-события от расширений браузера/HMR), но также означает, что если
   формат `GameResult` в Rust когда-нибудь разъедется с `CyberhackResult` в TS, это
   не будет замечено ни одним тестом — просто `onComplete` тихо не вызовется.
4. **`server-authoritative` режим — это соглашение, а не гарантия.** Компонент и
   wasm-ядро лишь передают сырые данные (`matrix`, `targets`, `path`) наружу; сам
   Cyberhack ничего не подписывает и не шлёт на сервер напрямую. Если потребитель
   пакета (например фронтенд, который встраивает `<Cyberhack>`) забудет отправить
   `sessionId` + `result.path` на бэкенд и вместо этого понадеется на
   `result.total_coins`, это станет дырой для накрутки наград — но с точки зрения
   самого Cyberhack-репозитория это не баг, а особенность контракта, о которой
   нужно помнить в местах интеграции (см. комментарии в `src/lib.rs` вокруг
   `GameResult`/`end_game`).
5. **`redirect_url: ""` как флаг "не редиректить"** — не самое очевидное API
   (магическая пустая строка вместо, например, `Option<String>`/пропуска пропа).
   Задокументировано в README и в комментариях в коде, но легко забыть при новой
   интеграции и словить нежелательный `location.assign("?coins=N")`.
6. **`main.css` (1200+ строк) — сгенерированный Tailwind-файл, лежит в git.** Это
   вывод `watch:css`/`build:css` для debug-страницы; при изменении `styles.css` не
   забывать пересобрать, иначе `trunk serve` покажет рассинхронизированный CSS.
7. **`trunk` не входит в зависимости пакета** (это отдельный Cargo-бинарь,
   `cargo install trunk`), из-за чего `pnpm run dev` из чистого окружения (например,
   свежий CI-контейнер) упадёт с "команда не найдена", пока кто-то не поставит Trunk
   вручную. В `package.json`/README это явно не подчёркивалось до этой правки.
8. **`pnpm-workspace.yaml` в момент написания этого документа не добавлен в git**
   (untracked). Он содержит только `allowBuilds` для `@parcel/watcher` — по всей
   видимости, реакция на pnpm-политику одобрения build-скриптов зависимостей. Если
   он пропадёт/не будет закоммичен, `pnpm install` в чистом окружении может начать
   интерактивно спрашивать одобрение постинсталл-скриптов или собирать
   `@parcel/watcher` иначе, чем ожидается.

## Если что-то сломалось — проверь тут в первую очередь

1. **`Cyberhack.tsx` пишет в консоль "WASM-модуль еще не собран"** → значит `pkg/`
   пуст или устарел. Решение: `pnpm run build` (или хотя бы `pnpm run build:wasm`).
   Помни, что `pkg/` не в git — после `git clone`/`pnpm install` его нужно собрать
   заново на любой новой машине.
2. **Игра рендерится дважды / появляется лишний экземпляр прямо в `<body>`
   продового приложения** → значит wasm собран БЕЗ `--no-default-features`, т.е.
   включена фича `standalone-debug` (она в `Cargo.toml` включена по умолчанию).
   Проверить, что используется именно `pnpm run build` / `build:wasm` из
   `package.json`, а не голый `wasm-pack build`.
3. **После окончания партии происходит нежелательный `location.assign(...)`/полный
   релоад страницы** → проверь, что `redirectUrl` явно передан пустой строкой `""`
   в интеграциях, которые сами обрабатывают результат через `onComplete`. Смотри
   комментарий вокруг `end_game` в `src/lib.rs` — там подробно описан именно этот
   баг, который уже когда-то чинили (коммит `01e1870`).
4. **Награда/результат не совпадают с тем, что ожидает бэкенд** → проверь, что
   бэкенд действительно в server-authoritative режиме реплеит `result.path` по
   собственной копии `matrix`/`targets`, а не читает `result.total_coins` напрямую
   (последнее — заведомо небезопасно и предназначено только для офлайн/дебажного
   отображения).
5. **`cargo test` падает** — единственный быстрый способ проверить, что базовая
   игровая логика (генерация доски, награда, i18n-фолбэк) не сломана. Начни отсюда,
   прежде чем копать в React/wasm-обвязке.
6. **Стили не применились / выглядят "не той" темой** → не перепутай `styles.css`
   → `main.css` (debug-страница, `trunk serve`) с `pkg/cyberhack.css` (то, что
   реально импортирует потребитель npm-пакета как `cyberhack/cyberhack.css`). Это
   два разных файла с разным жизненным циклом сборки (`build:css` собирает именно
   `pkg/cyberhack.css`; `watch:css` — `main.css`).
7. **Не устанавливается / странно ведёт себя `pnpm install`** → проверь наличие и
   содержимое `pnpm-workspace.yaml` в корне (см. пункт 8 в разделе "Грабли") — на
   момент написания этого документа он untracked, легко может потеряться при
   неаккуратной работе с git.
